## P1：核心监控与保护（功能完善的前提）

没有这些，主站无法安全地用于实际机器人控制。

### 必要的监控
- [x] **电流监控**（6078h）- P4.3 完成：SDO 观测线程约 50ms 周期读取，填入报告字段
- [x] **母线电压监控**（6079h）- P4.3 完成，同上
- [x] **温度监控**（200Bh:01h MOSFET / 200Bh:02h 电机）- P4.3 完成，同上
- [x] 位置、速度、力矩反馈（已有）
- [x] 跟随误差监控（已有）

注：以上三个量因 ESI 将对应模块声明为 `Fixed="true"` 且 `supports_pdo_configuration=false`，
无法映射进 TxPDO，走 SDO 慢速通道（约 3ms 往返）。观测线程在周期外读取，
周期线程只做加锁拷贝，不阻塞实时路径。

### 异常检测
- [ ] **碰撞检测**（电流突变）
- [ ] **卡死检测**（目标在变但位置不动）
- [ ] **过载检测**（持续高电流）
- [ ] **过热检测**（温度超限）
- [ ] **欠压/过压检测**
- [ ] **编码器故障检测**
- [x] WKC 错误检测（已有）
- [x] 周期 deadline 检测（已有）

### 持续运行能力
- [x] **持续运动验证**（连续数小时接收位置指令）- P1.6 完成，300s CSP 双轴保持位置，wkc_error=0
- [x] **实时性保证**（持续高频命令下的周期稳定性）- P1.4 完成，15 分钟 idle，deadline_missed=0
- [ ] **命令队列管理**（队列满时的策略）

## 当前状态总结

- **P0（基础）**：完成，CSP 模式可用
- **P1（核心）**：持续运行已验证（P1.4/P1.6 完成）；电流/电压/温度监控已实现（P4.3 SDO 观测线程）；
  异常检测判据（碰撞、卡死、过载、过热、欠压/过压、编码器故障）尚未实现
- **P2（多模式）**：CSV/CST 代码接口存在但未真机验证（P5.3 硬件阻塞）
- **P3（故障恢复）**：Fault Reset 调用路径存在但未长时验证（P2.5 硬件阻塞）
- **P4（诊断）**：运行报告和命令服务器已实现，协议规格见 `docs/protocol/command-protocol-v1.md`
- **P5-P6**：基本未实现

**下一步重点**：P1 监控能力（电流/电压/温度 SDO 轮询）或直接对接工程应用（P6 已完成，协议文档和安全约束齐备）。

## 已知代码缺陷

以下是当前代码中已识别但尚未修复的问题，按影响分类。

### 功能未实现

（暂无。此前的 P4.3 SDO 慢速通道条目已移除——该功能已于 2026-09-12 实现并有实机日志佐证。）

### 已修复（2026-09-14，台架复现后定位）

**停机路径的安全输出可能一次都发不出去**
- 影响：`report.safe_output_sent` 为 false 时，主站仍输出"已尝试发送安全输出"。上一轮台架运行
  （`status_code=19` CONTROLLER_FAILED）就是这种情形：状态字解不出来 → 停机路径重新解码同一个
  状态字 → 协调器拒绝整帧 → `stop_process_data` 在发帧前返回，实际一个停用帧都没发。
- 修复：停机路径不再经过多轴协调器，逐轴用 `emaster_cia402_controller_step` 在固定的 SAFE_STOP
  目标下计算输出；该路径对未知状态只产生 Disable Voltage（0x0000），不会发出任何使能位。
- 附带：`safe_output_sent` 改为仅在交换号确实推进时置位，周期时钟恢复跳过的整帧不再冒充已发送。
- 附带：失败末行不再无条件声称"已尝试发送安全输出"。通信不可用（WKC/DC/截止时间/周期等待失败）时
  停机路径整个不执行，此时输出"未发出安全输出（通信不可用）"，与报告里的 `safe_output_sent` 一致。

**停机路径的序号单调性检查必然失败**
- 影响：旧代码复用 `report->cycle_count + 1` 作为帧序号，该值在停机过程中不推进；协调器要求
  序号严格递增，所以第二次停机交换必然 `SEQUENCE_NOT_MONOTONIC`。第一轮就成功时不会暴露。
- 修复：同上，停机不再走协调器。

**运行时故障无现场记录**
- 影响：`first_cycle_failure` 只覆盖周期交换自身的失败；协调器拒绝、轴健康检查和使能确认
  这三类 CONTROLLER_FAILED 不留下任何现场，事后只能从一句笼统的失败消息反推。
- 修复：报告新增 `first_runtime_failure`，在 `latch_failure` 汇聚点首次锁存时抓取周期号、
  交换号、协调器判定和逐轴的原始状态字／控制字／解码状态／`state_known`／`fault_present`。

**同一次周期超时，因检出位置不同而结局相反（且不留现场）**
- 影响：`emaster_cycle_clock_sample` 在交换函数末尾（`session_exchange.c`）和循环顶部
  （`session_control.c`）各调用一次，两者是同一个条件、同一个 deadline，只相差本次输入解码与
  审计的开销（几十微秒）。交换函数内检出会走容错策略（`default` 策略 `enabled=true`、阈值 10，
  本会恢复并继续）；循环顶部检出却直接返回 29，既不查策略也不写现场。
- 台架证据（2026-09-14 三轴 30° 运行，24278 周期后终止）：全轮"发后工作块"（收包 + 邮箱推进 +
  3 次错误计数器 FPRD）p99.9 = 377 µs，唯一异常周期 1068 µs，该周期 `actual_wkc = -1`
  （SOEM `EC_NOFRAME`，帧根本没回来）。报告同时出现 `deadline_missed_count = 0`、
  `cycle_deadline_missed = true`、`first_cycle_failure = null` 三处互相矛盾，正是这条路径既不
  记账也不记录周期级失败所致。
- 修复：两个检出点共用 `emaster_soem_session_note_deadline_missed` /
  `emaster_soem_session_try_deadline_recovery`。循环顶部可恢复时不推进协调器（`deadline_ns` 已失效，
  喂进去会被判成整帧逾期并清空输出），重新对齐后回循环顶部；不可恢复才锁存失败，并同样发布反馈。
- 附带：新增"连续跳过上限"（取策略的 `deadline_recovery.consecutive_error_threshold`）。没有它时，
  若工作块持续超限，会话会每周期都在此处跳过协调器——既不推进也不终止，比直接停机更糟。

**遗留（未修复）**
- 单周期内的阻塞超时预算超过周期本身：收包 250 µs + 邮箱推进 + 3×`ecx_FPRD(0x0300)` 各 250 µs
  ≈ 1.25 ms > 1 ms 周期上限。因此只要丢一帧，本周期必然超限；上述修复只保证它被恢复而不是终止，
  没有缩短这次超限本身。缩小 FPRD 超时、或在丢帧周期跳过错误计数器读取，都能把预算压回周期内。
- P4.3 观察线程与周期线程共用同一个 SOEM context/socket 做邮箱往返，与 `session_internal.h`
  声明的"所有 SOEM 访问由会话线程串行执行"相矛盾。两轮台架的丢帧率（1/24278、12/173133）
  远低于常态争用应有的量级，所以它大概不是肇因，但仍是待修的并发缺陷。
- 丢帧根因无定论：报告没有亚步骤计时（收包／邮箱／FPRD 各自耗时），无法区分链路抖动、
  主机调度停顿和 socket 争用。

**三轴 30° 长时运行在停机阶段以 `SAFE_STOP_FAILED` 结束，三个驱动器全部掉出 OP**
- 台架证据（2026-09-14，上面那条修复之后同一部署，173133 周期 / 173 s，由人为 SIGINT 结束）：
  最后 5 次交换连续 WKC 不符（期望 9、实际 3，三个从站只有一个在计数），且全部发生在
  `safe_stop` 阶段（`first_cycle_failure.phase = safe_stop`，交换号 173133）。`safe_output_sent = true`
  ——停用帧确实发出，上一轮修的停机路径在实机上成立；但 `safe_state_reached = false`，没有一轴
  在切换超时内确认停用。停机后 `ecx_readstate` 读到三轴均为 AL state=20（SAFE-OP）、
  AL status code=26（0x1A 同步错误），而驱动器级诊断全零（603F=0x0000、1001=0x00、
  203E/203F=0x00000000）。即三个驱动器是**掉出 OP**，不是硬件故障。
- 与之吻合的时序异常：全程 173133 个周期中，逐轴有 4/4/5 个周期帧到达晚于 SYNC0
  （`sync0_margin_ns < 0`，最差 -33 µs；正常 p50 约 +200 µs），即主站输出确实在这些周期
  越过了驱动器的同步窗口——这正是 AL 0x1A 掉出 OP 的经典触发条件。
- 不能算证明的地方：聚合统计只给总量、不给位置，无法知道这 4/5 个迟到周期对应哪些交换号；
  而**最后一个周期的裕量是健康的**（+201.7 µs，相位误差 -1.7 µs，往返 183 µs）。所以"迟到
  导致掉出 OP"目前只能算吻合。本轮最差往返 1.08 ms、截止超时 2 次（均已恢复）。
- 本次调查发现并已补齐的观测缺口（2026-09-14）：
  - `sm2_diagnostic` / `sm3_diagnostic`（驱动器自身的 1C32/1C33 同步违例计数器：`sync_error`
    位、SM event missed、cycle time too small、shift time too short）此前在停机时读进会话结构
    （`session_shutdown.c:208-210`）却不进报告——最直接的证据被读出来又丢掉。现写入报告逐轴字段。
  - `sync0_late_count` 此前只计数不记位置。现增加 `first_sync0_late_exchange` /
    `last_sync0_late_exchange`，把迟到与 WKC 异常、驱动器掉出 OP 放在同一交换号坐标上对齐。
- 仍未处理的两条缺口：
  - 周期回路对 `sync0_margin_ns < 0` 不做任何反应（`emaster_cyclic_timing_last_sample_is_safe`
    只在启动阶段 `session_start.c` 使用）：主站明知本周期输出对驱动器已经迟到，仍照常推进。
  - `emaster_soem_pop_error_safe` 无调用者：SOEM 自己的错误环（状态变化、超时，带时间戳）
    从未被取用，等于放弃了总线侧唯一带时序的记录。
- 仍未定位的是"0.2 ms 量级的迟到从何而来"：非实时内核上的主机调度停顿、以及上面那条 socket
  共用争用都是嫌疑，现有报告无法区分。

**遗留的诊断盲点**：`stop_process_data` 返回 false 时仍不记录原因（是交换失败还是驱动器始终
未到安全停止态），目前只能靠 `safe_output_sent` 与 WKC 统计间接区分。待下次台架复现时再补。
