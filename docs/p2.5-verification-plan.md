# P2.5 单轴故障恢复验证计划

## 验证目标

确认单轴故障隔离和恢复机制在实际硬件上的行为：
1. 单轴故障时其他轴是否继续运行
2. 恢复命令是否能使故障轴重新上线
3. 驱动器和总线的实际响应

---

## 前置条件

- 双轴系统（OrangePi + 2台驱动器）
- 代码版本：0f2f52e 或更新
- 编译完成的 `emaster-master` 和 `emaster-control` 工具

---

## 测试场景

### 场景 1：人工触发单轴故障

**目的**：验证故障隔离逻辑

**步骤**：
1. 启动双轴控制会话（orangepi_bench.json）
2. 等待两轴进入 Operation Enabled
3. 使用 `emaster-control` 发送命令强制轴0进入 Quick-Stop：
   ```bash
   echo "quick_stop 0" | nc -U /tmp/emaster-cmd.sock
   ```
4. 观察终端输出

**预期结果**：
- 终端输出 `[P2.5] 轴0 故障隔离: 原因=X, 周期=Y`
- 轴1继续运行（PDO 交换正常，无 WKC 错误）
- 会话不退出

**失败模式**：
- 如果两轴都停止 → 隔离逻辑未生效
- 如果 WKC 错误 → 总线通信受影响
- 如果会话退出 → `ALL_AXES_FAULTED` 逻辑触发过早

---

### 场景 2：单轴恢复流程

**目的**：验证恢复状态机

**步骤**（接场景1）：
5. 发送恢复命令：
   ```bash
   emaster-control recover-axis 0
   ```
6. 观察终端输出和驱动器状态

**预期结果**：
- 终端输出 `[P2.5] 轴0 恢复流程已启动`
- 约1-2秒后，输出 `[P2.5] 轴0 恢复成功，重新启动`
- 轴0重新进入 Operation Enabled
- 两轴同时运行

**失败模式**：
- 如果超时（5秒无响应） → 驱动器未响应 Fault Reset
- 如果轴0停在 Switch On Disabled → 状态机卡住
- 如果轴0报错 → 驱动器拒绝恢复

---

### 场景 3：物理故障触发

**目的**：验证真实故障的处理

**步骤**：
1. 启动双轴会话
2. 断开轴0的编码器信号（或短路驱动器使能线）
3. 观察行为
4. 恢复硬件连接
5. 发送 `recover-axis 0`

**预期结果**：
- 轴0自动进入故障隔离（检测到 fault_present）
- 轴1继续运行
- 恢复硬件后，恢复命令成功

**失败模式**：
- 如果两轴都停 → 隔离失败
- 如果驱动器不响应恢复 → 需要断电重启（设备限制，非主站问题）

---

### 场景 4：两轴同时故障

**目的**：验证 `ALL_AXES_FAULTED` 逻辑

**步骤**：
1. 启动双轴会话
2. 依次发送：
   ```bash
   emaster-control quick-stop 0
   emaster-control quick-stop 1
   ```
3. 观察会话是否退出

**预期结果**：
- 终端输出两次故障隔离消息
- 会话输出 `所有轴故障`
- 会话退出（status = EMASTER_CONTROL_SESSION_ALL_AXES_FAULTED）

**失败模式**：
- 如果会话不退出 → 检查健康轴计数逻辑

## 关键观测点

### 1. 终端输出

搜索关键字：
- `[P2.5] 轴X 故障隔离`
- `[P2.5] 轴X 恢复流程已启动`
- `[P2.5] 轴X 恢复成功`
- `[P2.5] 轴X 恢复超时`

### 2. WKC（Working Counter）

正常双轴 WKC = 4（每轴2：输出+输入）

**单轴故障后**：
- 如果 WKC 保持 4 → 故障轴仍在总线上，PDO 继续交换
- 如果 WKC 降至 2 → 故障轴离线（硬件断连，非软件隔离）

### 3. 驱动器 LED

**隔离后的轴**：
- 绿灯闪烁 → Quick-Stop Active
- 红灯常亮 → Fault

**恢复后的轴**：
- 绿灯常亮 → Operation Enabled

### 4. JSON 报告字段

每轴报告新增字段（`emaster_control_session_axis_result_t`）：
```json
{
  "axis_status": 0,          // 0=NORMAL, 1=FAULTED, 2=RECOVERING
  "fault_isolated": false,
  "fault_cycle": 0,
  "fault_reason": 0
}
```

检查故障轴的报告是否正确记录。

## 硬件依赖验证

### 需要确认的驱动器行为

| 行为 | 期望 | 实际 | 影响 |
|------|------|------|------|
| Quick-Stop 后其他轴继续运行 | 是 | ? | 如果否，需要全局停止 |
| Fault Reset 仅影响目标轴 | 是 | ? | 如果否，无法单轴恢复 |
| 恢复后轴可重新上电 | 是 | ? | 如果否，需要断电重启 |
| WKC 在单轴故障时稳定 | 是 | ? | 如果否，总线不稳定 |

### 如何记录实际行为

在终端输出中添加调试信息：
```bash
# 修改 session_control.c 临时添加
fprintf(stderr, "[DEBUG] WKC=%d, expected=%d\n", wkc, session->expected_wkc);
```

或者使用现有的审计报告查看 `wkc` 字段。

## 测试命令快速参考

```bash
# 1. 启动会话（后台运行）
sudo ./build/tools/master/emaster-master \
  --deployment config/deployments/orangepi_bench.json \
  --motion none &

# 2. 查询状态
./build/tools/control/emaster-control query-status

# 3. 触发单轴 Quick-Stop（模拟故障）
./build/tools/control/emaster-control quick-stop-axis 0

# 4. 恢复单轴
./build/tools/control/emaster-control recover-axis 0

# 5. 查看日志（查找 P2.5 消息）
sudo journalctl -f | grep P2.5

# 6. 停止会话
./build/tools/control/emaster-control shutdown
```

## 待实现功能

当前实现的限制：

1. **命令工具未实现 recover-axis**
   - 需要在 `tools/control/main.c` 添加命令解析
   - 需要发送 `EMASTER_COMMAND_RECOVER_AXIS` 到套接字

2. **quick-stop-axis 命令不存在**
   - 当前只有 `quick-stop` 全轴命令
   - 需要添加单轴 Quick-Stop 命令用于测试

3. **JSON 报告未包含 P2.5 字段**
   - `axis_status`、`fault_isolated` 等字段需要添加到 `report_sections.c`

4. **恢复超时固定为 5 秒**
   - 应从部署配置读取
   - 当前硬编码在 `check_recovery_progress()` 中
