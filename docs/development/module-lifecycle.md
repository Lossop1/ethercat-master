# 模块开发生命周期

## 目的

EtherCAT 硬件可能把错误的软件假设转化为机器人失控。因此开发必须逐个完成可独立审查的模块。
编译通过不能作为模块完成条件。

## 强制顺序

每个模块必须按以下顺序交付：

1. 记录范围、明确的非目标、输入、输出、时序类别和安全边界；
2. 定义强类型接口、所有权/生命周期规则和封闭的错误模型；
3. 对正常、边界和失败行为实现不依赖硬件的单元测试；
4. 涉及协议行为时增加回放或仿真测试；
5. 通过严格编译告警、静态分析、代码审查和依赖检查；
6. 按书面流程只执行已授权的硬件状态转换；
7. 保存软件版本、配置哈希、原始结果和评审结论；
8. 冻结接口后，下一个模块才能跨越该边界。

后续模块不能替前置模块掩盖未解决的故障或含糊契约。任何假设发生变化，都必须重新打开受影响
的门槛并评审下游影响。

## 完成检查表

只有以下问题全部回答“是”，模块才可以标记完成：

- 需求和非目标是否可测试？
- 是否由一个明确的 CMake target 拥有实现？
- 依赖是否单向且最小？
- SOEM、操作系统、文件、日志和内存分配调用是否限制在允许的层和时序类别？
- 畸形输入和所有外部故障是否按失效关闭处理？
- 测试是否覆盖公开契约，而不是依赖私有实现细节？
- 硬件行为是否限制在已批准的 EtherCAT AL 状态？
- 证据是否能由指定版本和配置复现？
- 负责人是否审查并接受剩余风险？

## 项目交付顺序

| 顺序 | 模块 | 进入下一步前必须具备的证据 |
|---:|---|---|
| 1 | 设备目录 | ESI/校验和验证和目录单元测试 |
| 2 | PRE-OP 发现与指纹 | 离线格式测试和已批准的物理指纹 |
| 3 | 拓扑验证器 | 任意规模契约测试、每位置不匹配测试和独立的 12 轴产品证据 |
| 4 | PDO 布局与编解码 | 字节级黄金向量和畸形布局测试 |
| 5 | SOEM 映射与零输出 SAFE-OP | 独立授权和零输出硬件记录 |
| 6 | 分布式时钟 | 同步实测结果和已解决的 `1C32/1C33` 契约 |
| 7 | 周期引擎 | 回放/故障注入测试和实时指标证据 |
| 8 | CiA 402 单轴状态机 | 任何使能测试之前完成状态/转换穷举测试 |
| 9 | 安全监督器 | 联锁、超时、通信丢失和停机策略证据 |
| 10 | 多轴协调器 | 12 轴原子命令/反馈和部分故障测试 |
| 11 | 外部 API | 截止时间、序号、生命周期和传输隔离测试 |

第一阶段目前只涵盖顺序 1 至 3 的部分工作。在 `docs/requirements/phase-1.md` 中的所有门槛满足
之前，第一阶段不能标记完成。
