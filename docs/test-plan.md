# 测试方案与采集记录

本文件统一维护测试方法、通过条件、已有证据与待执行工作；项目实现和使用说明见 [README](../README.md)。本次整理日期为 2026-10-09，**没有执行新的真机测试**。

前半部分是后续统一执行的测试方案 v1.0；后半部分保留历史探索记录。历史“通过”只代表当时的判定，不能直接替代本方案验收。正式范围为固定拓扑、固定版本、1 ms DC、CSP 位置控制；CST/CSV、热插拔和功能安全认证不在范围内。

## A. 结论边界与测试路线

最终采用“离线检查 → 环境及证据检查 → 启停 → 短时保持/运动 → 单轴隔离 → 观测对照 → 故障行为 → 长时运行”的顺序。前一阶段失败先定位，不直接用加长运行或放宽保护阈值掩盖问题。

当前数据足以说明已经实现多轴运动及部分异常采集，**不足以说明 12 轴 1 ms 长期稳定**。900 s 仅有两轮完整记录；运动系列混入了启动拒绝、人工干预和版本变化。温度、运动精度的产品限值仍缺少需求或厂商依据。

本方案固定方法、轮数、数据口径与工程稳定性门槛。产品运动精度、热限制和允许停止时间在 B 节登记前，对应验收状态为 BLOCKED；不得临时用观测到的最大值作为合格线。

## B. 冻结测试条件

正式系列以台架自己的部署为基准（下文记作 `<你的部署ID>`）：12 轴、1 ms、DC、CSP、30°输出轴往返、单程 5 s、100 Hz 客户端、triangle、全部轴运动、观测开启、轮间 60 s。保持测试沿用同一部署但不发运动目标。先确认实际拓扑及各轴换算与部署匹配；12 轴并非其它台架可直接照搬的条件。

`<你的部署ID>` 不是仓库里的常量 —— 交付时六族配置是空的，这一份由你在现场用
`python gen/emaster_config.py init-site` 生成（见 `README.md` 的"快速上手"与"配置模型"两节）。
**带轨迹的系列还要把运动方案挂到这份部署上**（`init-site --motion <运动方案 ID>`），
不然部署是空闲档，客户端发目标才动、内置轨迹一次都不跑。换台架就换一份，
所以本文的命令里出现的都是这个占位符，不是某个具体名字。

每个系列记录以下内容，任一改变均创建新 SERIES，禁止混合统计：

| 类别 | 必须记录 |
| --- | --- |
| 软件 | Git commit、工作区差异、SOEM 版本、二进制 SHA-256、构建类型与编译器 |
| 配置 | 部署引用的完整 JSON 快照及哈希，不仅记录 ID；配置重新构建的证据 |
| 主机 | 内核/RT、CPU 频率策略、实时核/优先级、IRQ 亲和性、网卡驱动、卸载/合并设置、后台负载 |
| 装置 | 物理轴标签到环序映射、身份/固件、每轴齿轮比和编码器读回、供电、负载、接线及初始温度 |
| 条件 | 全部参数显式填写；计划/实际时长、开始结束时间、供电周期、人工操作及异常 |
| 待冻结需求 | 每轴最大跟随误差 E、稳态误差 S、稳定时间、温度/电压范围、最大允许停止时间；填来源及版本 |

运动限幅和软件保护值用于运行保护，不自动等于 E/S。30°运动、50°跟随误差护栏可能使不动的轴也不触发保护。历史 `series_verdict.py` 的半位移判据只适合筛查明显异常，不是精度验收或“不动”的因果证明。

## C. 统一判定与统计

每轮分别记录测试结果和故障分类，不只记录退出码：

| 结果 | 定义 |
| --- | --- |
| PASS | 条件、证据完整，全部适用判据满足 |
| FAIL | 条件成立且有证据违反判据，包括正常稳定性轮中的意外退出或启动失败 |
| INVALID | 人工断电、改线、错误部署等污染该轮；保留并说明原因，追加轮次，不抹掉原记录 |
| BLOCKED | 必需证据、测量能力或需求阈值缺失，不能判断 |

计划内的错误配置/断连注入属于负向测试，按预期拒绝或停机判定，不能归作 INVALID。正常配置下偶发身份读失败仍是启动失败，不应为了提高通过率剔除。

稳定性轮的门槛：实际运行窗口达到计划值；全轴正常进入 OP 和使能；稳态 WKC 与实际过程映像推导的期望值一致；无短帧、无整帧缺失、无 deadline missed/over budget、无意外驱动故障、无目标流超时；停机有全轴有效停用证据。当前映像常见 WKC=3×轴数，仅作交叉核对，不把它当所有 PDO 布局通用公式。

恢复策略容许的异常仍使“无异常稳定性”项目失败，但可作为“恢复行为正确”的证据，两种结果分别记录。默认连续阈值和滑窗阈值以本轮配置快照为准，不等于允许故障率。

运动判定逐轴进行：保存下发目标与实际位置，确认行程、方向、往返端点、跟随误差、保持误差；先用实测换算转成输出轴度数，再与 E/S 比较。仅凭 `all_enabled`、WKC、命令 ACK、`motion_completed` 或肉眼看起来在动均不充分。`ONLY_AXIS=N` 时对该轴检查行程，对其它轴检查保持误差，不能套用全轴运动判据。

停机判定须有每轴控制字写入及后续状态字有效读回，并符合配置的停用掩码；未读到、旧值、`still_enabled=false` 但读回无效，都不能算成功。AL INIT 不代表电气断能。记录停止请求到停用确认的时间；没有允许停止时间或有效计时则不能宣称满足响应时间要求。

统计按条件分组，报告计划/执行/PASS/FAIL/INVALID/BLOCKED 轮数、实际稳态总时长、实际有效周期数、首次异常时间、异常累计/最长连续/窗口峰值及逐轴结果。失败轮真实运行时间必须保留。启动和停机区间单列，不能用总周期数冒充运动时长。不把周期当作独立可靠性试验，也不把零故障 8 h 外推为 MTBF 保证。

表中轮数是本版工程验收计划，不是已有完成记录。所有项目当前均需在冻结版本下重新执行。

| 编号 | 执行条件与规模 | 通过依据 |
| --- | --- | --- |
| F0 离线回归 | 配置校验、Linux 构建及 CTest；配置链/分析工具/报告有效性检查各一次 | 全部适用检查通过；不依赖台架 |

| F2 启停重复性 | 保持 10 s，间隔 0/20/60 s 各 10 轮 | 30 轮均正常启动、完整停用；脚本固有启动/清理耗时另记，GAP=0 不代表实际间隔为零 |
| F3 保持稳定性 | 60 s × 3、300 s × 3、900 s × 3，依次推进 | C 节无异常门槛及逐轴保持误差 |
| F4 全轴运动 | 30°/5 s/100 Hz，60 s × 10，再 600 s × 3 | C 节无异常门槛、每轴 E/S/行程/方向均符合 |
| F5 单轴隔离 | 保持 12 轴接线，ONLY_AXIS=1…12，各 60 s × 3 | 被测轴运动正常，其余轴保持；比较异常是否随运动轴变化 |
| F6 观测开关 A/B | 同一硬件、同一运动，OBSERVATION=0/1，各 300 s × 5 对；交替 AB、BA 顺序 | 两组分别通过稳定性；比较时序分布与异常，不以单轮改善证明因果 |
| F7 客户端与停机 | status/目标/stop/shutdown；SIGTERM、客户端断开、超过配置的目标超时、重连各 3 次 | 实际行为与命令语义一致；失联不继续使用过期变化目标；无意外运动；逐轴停用可证 |
| F8 受控负向测试 | 错误身份/轴数、非法目标数量/范围各 3 次；受控通信中断各 3 次 | 非法请求不导致部分轴更新；错误部署拒绝启动；中断被记录并进入预期停止路径，无自动无条件复动 |
| F9 长时门槛 | 前项通过后：保持 1 h × 1、运动 1 h × 1；再选最终运行负载连续 8 h × 1 | 全程无异常、运动/热/电压/停机判据满足，完整证据无截断 |
| F10 数据自洽 | 每轮执行，故障轮重点检查 | 轴数、WKC、时长、计数、状态字解码、有效位/年龄、首故障与停机坐标一致 |

F8 的物理中断必须在受约束的台架和外部急停/STO 可用的条件下实施。通信完全中断时邮箱也不可用，不能期待软件保证断能；记录外部保护动作与逐轴状态。软件故障检测通过与整机安全停机通过必须分开。

F9 开始前先估算审计容量、报告体积、磁盘空间与归档保留量，检查丢弃/截断计数。现有脚本与内存审计并不自动保证适合 8 h；容量不足先完成采集能力准备，不能把数个短轮拼为连续 8 h。README 的延迟分位数和最大执行时间是设计目标；缺少相应原始直方图/计时定义时列 BLOCKED，不用 frame interval 冒充唤醒延迟。

## E. 执行命令与证据流程

先按 README 构建到 `build/`。以下命令在 Linux 台架仓库根目录执行。bench 脚本会清理其它主站，执行前必须确认专用台架没有活动会话。每轮结束先核对证据，再进行下一轮；如无法证明已停用则暂停系列，检查装置。

```bash
python3 gen/validate_project.py
python3 gen/emaster_config.py build --config config --out /tmp/config-runtime
diff -r config-runtime /tmp/config-runtime          # 逐字节相同 = 生成与配置内容无关
ctest --test-dir build --output-on-failure
python3 checks/config_chain_check.py
python3 checks/analysis_tools_check.py
python3 checks/report_telemetry_check.py
python3 checks/device_facts_check.py
python3 checks/pdo_assignment_check.py
```

第二条是"换电机不重编主站"的主断言：客户改配置只重新生成，不动二进制。所以生成物
必须与配置内容无关 —— `diff` 有输出就说明生成器沾了内容（时间戳、字典序、浮点格式），
那是先要修的东西，不是可以放过的噪音。

前两条合起来只证到"生成器不看内容"。要证"主站真的不看内容"，还得让**同一份编好的
二进制**把两套 flat 都装进去 —— 一套是交付的空的 `config-runtime`（0 份配置），一套是
客户从 ESI 从零生成的。`public_api_swap` 与 `deployment_apply_roundtrip` 的期望值全部
从交给它们的文件里读，不写死型号，所以换个 `--config-dir` 就是换一套判据：

```bash
# 用客户自己的配置生成一套 flat（先跑 add-device / init-site，见 README 的"配置模型"一节）
python3 gen/emaster_config.py build --config config --out /tmp/customer-runtime

# 不改一行 C、不重编，同一个可执行文件读两套
./build/tests/test_public_api_swap config-runtime/topologies.flat config-runtime/catalog.flat \
                                       config-runtime/runtime.flat config-runtime/deployments.flat
./build/tests/test_public_api_swap /tmp/customer-runtime/topologies.flat \
                                       /tmp/customer-runtime/catalog.flat \
                                       /tmp/customer-runtime/runtime.flat \
                                       /tmp/customer-runtime/deployments.flat
```

两边的条数会不同（空配置是 0、客户的按他的设备数），但都必须"失败 0 项"。空配置下它
问的是"空是合法的可装载状态"，客户配置下问的是"访问函数报的和文件里写的一致"。

保持示例（对应 F3 的第一组，SERIES 每次使用新名称）：

```bash
sudo env REPO="$PWD" DEPLOYMENT=<你的部署ID> \
  SERIES=f3_idle60_v1_20261009a MODE=idle ROUNDS=3 GAP=60 \
  IDLE=60 OBSERVATION=1 bash scripts/bench_series.sh
```

运动示例（对应 F4 第一组）：

```bash
sudo env REPO="$PWD" DEPLOYMENT=<你的部署ID> \
  SERIES=f4_motion60_v1_20261009a MODE=reciprocate ROUNDS=10 GAP=60 \
  DURATION=60 TRAVERSE=5 DEGREES=30 RATE=100 WAVE=triangle \
  ONLY_AXIS=0 OBSERVATION=1 SETTLE_TICKS=10 REPORT_INTERVAL=10 \
  bash scripts/bench_series.sh
python3 analysis/series_verdict.py evidence/_f4_motion60_v1_20261009a
```

后续按 D 表改变时长/轮数并新建 SERIES。F5 每个轴独立命名并显式设置 `ONLY_AXIS`；F6 显式设置 `OBSERVATION`。故障注入、单轴保持和长时容量目前不能直接由 `series_verdict.py` 完成最终判断，须按 C 节逐项复核。

工具限制：`bench_series.sh` 返回 0 只表示系列循环结束；`series_verdict.py` 默认 WARN 不改变退出码，`--strict` 又会把 `motion_completed=0` 等历史语义问题一起判失败。两者都不是完整验收器；不得以单个退出码生成最终 PASS。

每轮保留脚本已有的 condition、device-identity、NIC 前后快照、日志、summary、row、exit-code、report-name。人工记录补充 B 节未自动采集的内容及下表；原始 JSON 另存可靠介质，并登记绝对存储位置和 SHA-256。归档有保留上限，不能只留文件名而任其轮转删除。

**当前脚本的证据关联风险**：系列脚本用归档目录最新文件和 latest 报告提取结果。若本轮启动失败而旧报告仍存在，可能串入上一轮数据。必须核对报告时间、部署、周期与本轮日志；匹配失败时标 BLOCKED，不能据旧报告判定本轮成功。

| 每轮人工结果字段 | 填写内容 |
| --- | --- |
| 标识 | F 编号、SERIES、轮次、版本与配置哈希 |
| 时间 | 计划时长、实际稳态时长、启停时间 |
| 判据 | 通信、时序、逐轴运动/保持、逐轴停用、遥测有效性分别判定 |
| 结论 | PASS/FAIL/INVALID/BLOCKED，依据与原始文件位置 |
| 异常 | 首次异常坐标、注入/人工操作、复现步骤、后续处理 |

结果登记在本文件的后续批次记录或已有系列证据中，不新增第三份项目说明文档。

| --- | --- |
| 900 s 仅两轮完整、混入断电/换线 | F3 重做三轮，污染轮单列 |

# 2 必须分清的两层状态

这一节是全天工作中**最容易搞错**的地方，单独列出。

| | EtherCAT AL（ESC 层） | CiA 402（驱动器层） |
| --- | --- | --- |
| 载体 | 寄存器 `0x0120` AL Control / `0x0130` AL Status / `0x0134` AL Status Code | 对象 `0x6040` 控制字 / `0x6041` 状态字 |
| 状态 | INIT 1｜PRE-OP 2｜SAFE-OP 4｜OP 8 | 八个状态，见 `include/emaster/cia/controller.h:10-18` |
| 通道 | INIT 无邮箱无 PDO｜PRE-OP 有邮箱｜SAFE-OP 有输入无输出｜OP 双向 | 邮箱（PRE-OP 及以上）或 PDO（仅 OP） |
| 谁管 | 主站的状态请求 | 驱动器的内部状态机 |

**两层互不决定。** 实测（2026-10-08）：AL 状态已是 **INIT**，而 12 台驱动器的 `0x6041`
全是 **`0x1237`**（Operation enabled + Voltage enabled）—— 电机保持着力矩，而总线这一层
早已退出 OP。

**推论，都吃过亏**：

1. **不能用 AL 状态推断驱动器使不使能。** 两个都要读。
2. **不能用 PDO 去送"停止周期通道"的命令。** PDO 只在 OP 下有效；从站一旦掉出 OP，
   控制字就到不了它。**禁用必须走邮箱。**
3. **AL 在 INIT 时读不到 `0x6041`**（邮箱关闭）。这时只能说"读不到"，不能用 AL 顶替。
4. **`0x0134` 只在 `0x0130` 的 bit4（Error Indicator）置起时才有意义。** 没有 error 位时
   读它等于没读。SOEM 只在看到 error 位时才去读，这是照规范做，不是偷懒。

**译名的依据只有标准。** 工具里印的 `switch-on-disabled` / `operation-enabled` 出自
CiA 402（IEC 61800-7-201）的位定义，**没有厂商状态表佐证** —— 厂商手册随电机走、不在仓库里，
而且它给的位名与标准不同（bit6 叫"伺服准备好"、bit2 叫"伺服运行"），与它自己的读数也不自洽。
**别拿厂商的位名去改这里的译名**：位定义只能照标准，厂商那张表是错的。

### 2.1 每款新电机必须先做的读数（接上就做，不动轴）

设备档里的 `safe_stop_status_mask` / `safe_stop_status_value` 是**唯一一条"给错不会有人
看出来"的配置**：它不出现在报告正文里，也不影响通信，只决定主站**判定"能不能安全停机"时
看状态字哪几位**。给错了，主站会在驱动器仍出力时报"全轴已安全"。所以它不能照标准默认值抄，
只能量。

台架上量过一条反常识的事实：**某款驱动器真使能时 `0x6041` 也读到 `0x1250`**，而
`0x1250 & 0x006F == 0x40 == switch-on-disabled` —— 照标准默认掩码会把它判成"已停"。
这不是所有驱动器都这样，但是"照抄默认值"这条路已经走不通的证明。

**读数项（每款型号一份，写进它的设备档）**：

| 状态 | 读什么 | 用来定 |
| --- | --- | --- |
| 未使能（伺服使能断、轴是松的） | `0x6041`、`0x6040`、`0x6061`、`0x608F` | `safe_stop_status_value` 的候选 |
| 真使能（听声音、手动推轴确认，见下） | 同上四个对象 | 掩码必须把这两态分开 |

**判使能只看两个真判据：有没有声音、轴松不松**（`0x6041` 也会骗人）。加力矩前先上机械防护。

两态读完之后：状态字在同一段掩码下取值不同的那些位就是掩码；取不出任何有区分度的位，
就把 `safe_stop_status_mask` 填 0（含义是"没有可靠的设备侧判据"，停机退化为标准 CiA 402
判据），**并在设备档和台架记录里写明这台设备属于这一类**。`gen/validate_project.py` 在
掩码为 0 时会打印一条告警，不是错误 —— 合法，但必须有人知道自己选了什么。

# 3 怎么采

## 3.1 命令

**单轮空转**（电机不动，只使能保持）：

```bash
sudo env DEPLOYMENT=<你的部署ID> IDLE=60 OBSERVATION=1 TAG=idle1 \
  bash scripts/bench_idle.sh
```

**单轮往返**（电机往复）：

```bash
  RATE=100 ONLY_AXIS=0 OBSERVATION=1 TAG=recip30 \

```

**多轮**（把证据收进仓库）：

```bash
sudo env DEPLOYMENT=<你的部署ID> SERIES=<系列名> ROUNDS=3 GAP=20 \
  MODE=idle IDLE=900 OBSERVATION=1 bash scripts/bench_series.sh
```

**`SERIES` 决定证据目录 `evidence/_<SERIES>/`。换个名字就不会覆盖上一批。**

## 3.2 每一轮的产物

```
evidence/_<SERIES>/
  index.tsv                  一行一轮（32 列）
  r01_<TAG>/
    condition.txt           本轮施加的条件（轴数/时长/节拍/间隔/是否运动）
    device-identity.txt     装置身份 + 主机上下文（中断、线程、负载）
    nic-before/after/diff   网卡收发计数（帧发出去多少、回来多少）
    anomalies.tsv           从主站日志抽出的异常表
    notes.md                人工观察
    <TAG>_master.log        主站日志
    summary.txt             report_summary.py 的输出（人读）
    row.tsv                 该轮在 index.tsv 里那一行
    report-name.txt         完整报告在归档里的文件名 ← 完整证据的坐标
```

**完整报告不入库**（空转 20 MB、运动轮 500 MB 量级），留在 `run_report_path` 的 `archive/` 下。
`index.tsv` 里的 `report-name.txt` 是找到它的坐标。

**来源分两层，不要混**：

| 来源 | 内容 | 主站不跑时有吗 |
| --- | --- | --- |
| **主站进程** | 运行配置与通信审计报告、主站日志、周期现场环 | **没有** |
| **外层脚本** | 条件、装置身份与主机上下文、网卡差分、异常表 | **有** |

## 3.3 判据从哪来

**不写死在代码里。** 容错阈值读 `config/error_recovery_policies/<id>.json`：

| 块 | 默认 | 含义 |
| --- | --- | --- |
| `wkc_recovery` | **连续 5**、60 秒窗口内 50 | 短帧 |
| `no_frame_recovery` | 同上 | 整帧未回 |
| `deadline_recovery` | 连续 10 | 周期截止点错失 |
| `al_state` / `cia402_fault` / `dc_late` | `enabled=false` | 未启用 |

**判据是"连续"，不是"累计"。** 实测里"散落 2 次"跑完、"连续 5 次"中止，区别只在连续数上。
**连续段是联合的**（整帧未回也计入连续），**窗口是分类的**（各推各的）—— 所以
`wkc_short_window_max` 可能小于 `wkc_max_consecutive`，那不是矛盾，是两个口径。

## 3.7 报告读法陷阱

1. **`wkc_no_frame` 与 `wkc_mismatch` 的计数口径不同。** 前者记录未取得有效回帧，后者记录过程数据 WKC 与预期不符。计数可帮助区分整帧缺失与非预期 WKC，但不能单独定位到链路、主机调度或某个从站。非预期 WKC 也不能直接等同于从站掉出 OP。
2. **`AL state=0` 不是"在 INIT"。** SOEM 的 `ecx_readstate` 先把缓冲清零再读，所以 0 只可能是**这一站没应答**。8 = OP、20 = SAFE-OP 加错误位、1 = INIT、**0 = 没读回来**。
3. **收尾那句 `OP=通过` 走地址 0 广播，只照见环上最后一站。** 判"哪几根不在 OP"要看逐轴快照（`shutdown_al_entry`）。
4. **按 `index.tsv` 的表头读取字段，不按固定列号统计。** 可运行 `series_index.py` 从关联报告重建索引，并核对时间字段的单位。

## 3.8 按阶段读指定对象

**审计段记录的是主站真的读过的对象。** 所以必须按阶段取，不能把停机后的读数当作运行期的值。

```bash
sudo python3 analysis/extract_report.py runtime/reports/<部署>-latest.json |
  grep -E '^axis[0-9]+\.(status_word|mode_display|target_position)\.'
```

```text
axis1.status_word.cyclic_operation=4663
axis1.status_word.cyclic_operation.hex=0x1237
axis1.mode_display.cyclic_operation=8
axis1.target_position.cyclic_operation=462644
```

键的形状是 `axis<N>.<对象名>.<阶段>=<十进制>`，另有 `.hex=<原始十六进制>`。

**为什么必须按阶段看**：`0x1237` 与 `0x1233` 的 bit2 不同，分别对应 Operation enabled 与 Switched on 的标准状态掩码。只看停机后的状态字不能推断运行期间是否使能。

**读法边界**：某个对象没有 `cyclic_operation` 这一项，说明**这份二进制在 OP 期间没有读它**，**不是"值没变"**。

# 5 按任务的结果

## T1 基线采集 —— 完成

每轮自动采装置身份与主机上下文。主机上下文里最要紧的一条：
**实时核（CPU 11）上有 21 个线程**，含 `ksoftirqd/11`、`kworker/11:0H-events_highpri`、
`migration/11`、`chronyd`、`gnome-shell`、`python3`；
`interrupts_on_rt_core = 351,802,032`，其中 `IPI1` 占 **52.7%**；网卡的 95.9 M 次中断
**全在 CPU 0**；`irqbalance` 未安装；网卡 32 个队列只用了一个。
`README.md` 第 2 节的 7 条主机要求里，**4 条明显未满足**。

## T2 启动边界 —— 完成（9 轮，全干净）

间隔 0 / 20 / 60 秒各 3 轮，全部退出码 0、**WKC 异常 0**。
**结论：这三种重启间隔下，主站都能干净起来。**

## T3 空转稳定性 —— 部分（900 秒只完成 2 轮）

| 时长 | 轮 | 退出码 | 实到拍 | WKC 异常 | 连续 | 首次异常拍 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 60 s | r01 | 0 | 72231 | 2 | 1 | 35255 |
| | r02 | 0 | 72728 | 0 | 0 | — |
| | r03 | **1** | **3222** | **5** | **5** | **3218** |
| 300 s | r01 | **1** | **90190** | **6** | **5** | **80617** |
| | r02 | 0 | 312705 | 0 | 0 | — |
| | r03 | 0 | 312714 | 2 | 1 | 250455 |
| 900 s | r01 | 0 | 912757 | 2 | 1 | 570258 |
| | r02 | 0 | 911912 | 1 | 1 | 659253 |

**被中止的两轮都在开头（3.2 秒、90 秒），而 900 秒两轮全部跑满。**

**但这个观察有一个陷阱**：被中止的轮，`first_mismatch_ex` 必然小 —— **它是被那次爆发中止的**。
"爆发出现在开头"与"这一轮很短"是同一句话。**只看被中止的轮是循环论证。**

**能验的是存活轮**：13 轮存活且有异常的轮里，首次异常落在整轮的
**13% / 29% / 43% / 44% / 48% / 49% / 51% / 55% / 57% / 58% / 59% / 62% / 65% / 72% / 80%** ——
**近似均匀，没有集中在开头。**

**所以"跑得越久越容易出问题"和"开头更脆弱"这两个说法，在这批数据上都不成立。**
样本 8 轮空闲、2 次中止，太少，只能记为未决。

> **统计这批数据时踩过的坑**：`index.tsv` 的列**随工具版本变化**。旧系列是 28 列（字段 18 是
> `frame_interval_max`，纳秒），新版是 32 列（字段 18 是 `first_mismatch_ex`，交换号）。

# 6 发现并修掉的缺陷

**全部有实测证据，全部已提交。**

## 6.1 退出时不真正禁用（安全缺陷）

**禁用（`0x6040 = 0x0000`）只走 PDO**，而 PDO 只在 OP 下有效。从站一旦掉出 OP，
那条禁用就到不了它，驱动器保持着最后一次收到的"使能"，**功率级继续带电**。

实测：AL 状态已是 INIT，而 12 台 `0x6041` 全是 `0x1237`。

**一条基本道理：不能用周期通道去送"停止周期通道"的命令。**

改法：停机诊断块里补一次**走邮箱**的权威禁用。验证：`0x1233 → 0x1250`，
**并且在一次真故障里生效**（`_t3idle900b/r01`，过程数据全断、停机各步全失败，邮箱仍把
12 台禁掉）。

## 6.2 启动时不先禁用

主站启动时对从站的既有状态不做任何判断，一上来就发 `INIT→PRE-OP`，**那一刻过程数据就停**。
若驱动器此刻使能着，它会带着使能、在"没有目标也没有被禁用"的状态下，等主站走完
PRE-OP → SAFE-OP → OP 整段（控制字要到 OP 才发得出去，SAFE-OP 下输出不生效）。

改法：PRE-OP 配置一开始先读 `0x6041`、再写 `0x6040 = 0x0000`。

## 6.3 禁用无法自证

两个缺陷叠在一起：

- **停机侧那次禁用排在每轴块末尾**，12 台 × 十几次邮箱往返之后，环上**最后两席操作全失败**
  （`statusword_before_read=false`）—— **禁用根本没发出去，那两台一直使能着**
- **启动侧只有写、没有写后读回**，而只看写调用的返回值不够：**写成功而驱动器没照做**，
  才是要抓的形状

**宣布"已验证"时我只看了**一根**轴的读数，而那根恰好成功。** 逐轴查才发现最后两席全失败。

改法：挪到每轴块第一位；两侧都补写后读回与 `still_enabled`。

## 6.4 空转脚本不监视主站

`bench_idle.sh` 的空转窗口原来是一句 `sleep "$IDLE"`。主站在第 227 秒自行退出后，
脚本又睡满 900 秒 —— 不报错、不落盘、不记录实际跑了多久，**从外面看就是卡死**。

改法：逐秒 `kill -0`，记下**实到秒数**，中途退出按退出码 2 上报。
**"计划 900、实到 227"这个差值本身就是最有用的读数。**

## 6.5 一次真实的崩塌

`_t3idle900b/r01`：第 **227340 拍** WKC 由期望 36 掉到 **10**，主站自行退出，
停机各步全失败（过程数据那条路已经断了）。
**它落在换线前后，不做归类。**
