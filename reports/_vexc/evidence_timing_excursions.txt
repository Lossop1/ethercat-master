# 探查记录 时序越界的来源与外宿上下文
# 日期 2026-10-08    部署 orangepi-bench-duodec-30deg

== 一、问题被量化了 ==

新增的两项记录（报告里的 timing_excursions，device-identity 里的宿主上下文）第一次跑就
把问题写成了一个数。vexcr02（空转 20 秒，2813 拍）：

  send_late_buckets = [2813, 0, 0, 0]     2813 拍全部发晚 < 10 us —— 一次没晚
  receive_buckets   = [2811, 1, 0, 1]     只有 1 拍收包 >= 250 us
  margin_buckets    = [2511, 255, 0, 47]  47 拍 sync0 裕量 < 50 us
  receive_slow_max_exchange = 2809        <- 正是窗口里那一拍

异常窗口（交换号 2808-2813）：
  2808  wkc=36   recv=105  lat=3  marg=200  fgap=1000
  2809  wkc=-1   recv=269  lat=3  marg=200  fgap=1000   <- 收包撞 250us 超时上限，整帧未回
  2810  wkc=13                       fgap=3000          <- 主站等满超时，跳过 3 拍
  2811  wkc=13

**2813 拍里只有 1 拍收包超时，而这一拍报废了整轮 57 秒。** 发生率 1/2813 = 0.036%。
链是：等满 250us 超时 -> 错过 3 个周期 -> 驱动器攒够 SM 事件丢失掉出 OP -> WKC 永久变短
-> 主站连续 5 拍检测到不符 -> 按策略中止。

而另有一条极值完全看不出来的：**47/2813 = 1.7% 的拍 sync0 裕量 < 50 us**（正常约 200 us）。
系统离边界比极值显示的近得多。极值只会说"最坏那一次是 269 us"，答不了"有多频繁"。

== 二、挤占实时核的不是网卡 ==

device-identity 新增的宿主上下文（21 天运行期的累计值）：

  interrupts_cpu_0  = 260,580,361
  interrupts_cpu_10 = 394,085,015
  interrupts_cpu_11 = 351,802,032   <- 实时核（配置 realtime.cpu_core=11）
  nic_irq_total     =  95,939,086   <- 网卡，全部落在核 0

分解实时核那 3.52 亿次：
  IPI1（Function call IPI，别的核喊它干活）  185,229,099   占 52.7%
  IRQ 12（GICv3 26）                        165,604,793
  合计约 192 次/秒 —— 1 kHz 周期下平均每 5 拍被打断一次。

核 11 当时住着 21 个线程：ksoftirqd/11、kworker/11:0H-events_highpri（高优先级工作队列）、
kworker/11:1H-kblockd、migration/11、cpuhp/11，外加 chronyd、evolution-alarm、gsd-power、
ibus-extension-、gcr-ssh-agent、python3。**实时核没有被隔离，上面是一个带桌面的系统。**
irqbalance 未安装（inactive / not-found），所以中断落点是内核默认值，没人配过。
网卡有 32 个队列，其中只有 0 号在用。

另外 nproc=12，配置把实时线程绑在核 11 —— 而核 11 恰好是中断第三多的核。

== 三、所以"晚一拍"是哪来的 ==

不是网卡（网卡 9600 万次全在核 0）。是**跨核干扰**：别的核通过函数调用 IPI 让核 11 干活，
外加一个每秒约 90 次的 GIC 中断。IPI 会抢占 SCHED_FIFO 线程，这是内核层面的抢占，
主站用什么优先级都挡不住。

== 四、没证到的 ==

  · 收包超时的那一拍"具体被什么打断"没有直接证据。现在的记录能给出发生率与坐标，
    给不出当时是谁在跑——需要 per-CPU 的中断时间线（ftrace / perf），而那种采样本身
    会挤占实时核，要先想清楚怎么取。
  · 47 拍裕量 < 50 us 是常态还是会恶化，一次 20 秒的样本答不了（T8 长时行为要回答的）。
  · 核 10 的中断比核 11 还多（3.94 亿），为什么这两个核特别多没有查。

== 五、这次改动的边界 ==

新增的分档计数只在越界侧细分，正常侧归第 0 档；边界值一并印进报告，读的人不必看源码。
分档边界是**测量粒度不是判定阈值**，改它们不需要走阈值批准（本来也没有阈值）。
连续段的判据取得比第 1 档更严（发晚 25us、收包 200us）：10us 级抖动在非实时内核上常见，
拿它当越界会让"最长连续段"恒等于运行的拍数，那个数就没有信息了。
