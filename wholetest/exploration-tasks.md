# 0 本文怎么用

本文只回答两个问题：**给它施加什么条件**，**以及在这个条件下把什么记下来**。

它不设通过线。不设通过线的理由是：要查的正是"它会在哪里、以什么形式出问题"，而这些事先并不知道。事先设一条线，只会让线外的现象被记成"失败"而不是被当作发现。

**一条探查结论的最低要求**：说清"在什么条件下、观测到了什么、这个现象可不可复现"。达不到这三条的不是结论，是印象。

判断"是否存在问题"的方法见第 6 章。**问题不是"低于某个值"，而是"没预料到、或与其它读数矛盾、或代价不可接受"。**

## 0.1 为什么以 12 轴为主

12 轴在**周期预算**上是这个系统的最坏情况：1 ms 内要完成的数据报条数、错误计数器读取额度、邮箱流量都随从站数增长。因此 12 轴通过的条件，在时序上覆盖了 1–11 轴的多数情形。

这个论点有两处不成立，探查时要知道：

1. **配置差异不随轴数缩放**。护栏（单轴档 2°、多轴档 50°）、换算、部署档都是逐档写的。12 轴档跑通不说明单轴档没问题。
2. **轴少时问题可能被掩盖**。一根轴不动，在 12 轴里是 1/12 的异常，在单轴里是整台失效。反之，单轴档的护栏更紧，会暴露 12 轴档放过的行为。

所以：**12 轴是主对象；降轴只作为对照点，且只取有理由的那几个**（见 T6.2）。

# 1 探查目标

按"想知道什么"列出，后面每个任务都对应到这里的一条或几条。

| 编号 | 想知道 |
| --- | --- |
| G1 | 这台装置现在**实际能连续运行多久**才出现第一次异常 |
| G2 | 异常**都有哪些形态**，各自长什么样 |
| G3 | 每种异常**首次出现时的第一现场**是什么（谁先动、谁是果） |
| G4 | 哪些异常是**必现**、哪些是**随机**；随机的大致频次 |
| G5 | 异常与**哪些条件**相关（重启间隔、是否运动、观测开关、节拍） |
| G6 | 系统的**容错边界**：坏几根还能继续；坏之后能否恢复 |
| G7 | **启动边界**：多少轴、什么节拍下能起来 |
| G8 | **长时行为**：是否随时间劣化 |
| G9 | 观测本身**是否影响被观测对象** |
| G10 | 各读数之间的**因果关系**（谁先谁后） |
| G11 | 上报的量**是否自洽**（同一事实在不同字段里说法是否一致） |

# 3 记录规范

探查的质量完全取决于记录。**验收只需记"够判定的量"，探查要求记"够发现没想到的问题的量"**，后者宽得多。

## 3.1 三组记录

| 组 | 内容 | 现状 |
| --- | --- | --- |
| 装置身份 | 第 2 章那五项 | **无采集点**，需新增 |
| 逐拍序列 | 帧计数、周期错失、同步裕量与相位、逐轴状态字与控制字、逐轴位置与跟随误差 | **只有极值与直方图**，无逐拍序列 |
| 事件 | 每次异常一条：类型、首次坐标、末次坐标、当时逐轴状态、伴随读数 | 部分有（`fault_timeline`），未覆盖帧类异常 |

## 3.2 逐拍序列的取舍

12 轴 × 1 ms 全程逐拍存下来，一小时是 4.3 亿拍，不现实。三种策略，按任务选：

| 策略 | 做法 | 用于 |
| --- | --- | --- |
| 全存 | 逐拍存，限定时长（如 60 s） | 定位"第一现场"的任务（T5） |
| 环存 | 内存环，异常发生时把异常前后各 N 拍落盘 | 长跑任务（T3、T4、T8） |
| 汇总 | 只留极值、直方图、事件坐标 | 长跑的常规轮次 |

**环存是这里最值得做的一项**：现在的现场环只有 64 拍且入环点在逐轴解码之前，异常前的关键几拍往往已经滚掉。建议改为"异常前后各 200 拍"。

## 3.3 每轮必须落盘的文件

```
<轮次目录>/
  device-identity.txt     第 2 章五项（新增）
  condition.txt           本轮施加的条件（新增；轴数/时长/节拍/间隔/观测开关/是否运动）
  master.log              主站日志
  client.log              客户端日志
  outcome.txt             单轮脚本全程输出
  report-name.txt         完整报告的归档坐标
  anomalies.tsv           本轮每个异常一行（新增；见 3.4）
  notes.md                观察者的现场记录（新增；含"没看懂的"）
```

## 3.4 anomalies.tsv 的列

| 列 | 含义 |
| --- | --- |
| `seq` | 本文件内序号 |
| `kind` | 现象类型（自由文本，但要能归并；见第 6 章的形态库） |
| `first_exchange` | 首次出现的交换号 |
| `last_exchange` | 末次出现的交换号（单次则同首） |
| `count` | 出现次数 |
| `axes` | 涉及的轴号列表 |
| `al_state` | 涉及轴的 AL 状态与状态码 |
| `frame_counts` | 当时的期望计数与实得计数 |
| `sync` | 当时的同步裕量与相位 |
| `follow_err` | 涉及轴的跟随误差 |
| `reproducible` | `yes` / `no` / `unknown` |
| `note` | 观察者补充 |

**`unknown` 是合法取值。** 取不到就写 unknown 或 na，不得以 0 代替——零在多数读数上是合法值。

# 5 任务详述

## T1 基线采集

**要回答**：这一轮跑的到底是什么机器、什么代码。

**为什么单列一个任务**：跨天或跨人的两次运行，没有这份记录就无法比较。它不是形式，是可比较性的前提。

**做法**：按第 2 章逐项采集，落 `device-identity.txt`。

**注意**：扫描工具会读 SDO，需要从站已上电且链路已建立。`carrier=0` 时扫描必然 0 台，不要把它当成"从站坏了"。

---

## T2 启动边界

**要回答**：12 轴能稳定进入运行态吗？重启间隔多短还能起来？

**条件**：12 轴、1 ms、DC。

**子任务**：

| 编号 | 条件 | 记录 |
| --- | --- | --- |
| T2.1 | 冷启动（断电后首次） | 启动各阶段耗时、DC 收敛用掉多少拍、各轴进入使能的顺序 |
| T2.2 | 背靠背重启，间隔 0 / 5 / 20 / 60 秒，各 5 次 | 每次是否进入运行态；未进入时的失败形态 |
| T2.3 | 启动失败后立即重试 | 重试能否成功；连续失败几次 |

**看什么**：

- 启动各阶段的耗时分布（尤其 DC 收敛拍数的波动）
- 失败时是"没进 OP"还是"进了 OP 又掉出来"
- 失败信息具体指向哪一轴、哪一项

**产出**：`T2_startup.md`：一张表（条件 × 次数 × 结果 × 失败形态）。

---

## T3 空转稳定性

**要回答**：不发任何目标，12 轴能连续运行多久才出现第一次异常？异常是什么？

**条件**：12 轴、1 ms、DC、观测开；不发目标。

**做法**：`bench_idle.sh`，时长 60 / 300 / 900 秒逐级。每一级至少 3 次。

**记录**：第 3.3 节全套；异常按 `anomalies.tsv` 格式。

**看什么**：

- **第一次异常出现的时间**（这是 G1 的主读数）
- 异常出现前若干拍的读数有没有前兆（环存的价值就在这里）
- 异常是否只在某几根轴上出现
- 若无异常，运行到多久才停（不要因为"没出事"就缩短）

**产出**：`T3_idle.md`：时长 × 次数 × 首次异常时间 × 形态。

---

## T4 运动稳定性

**要回答**：带运动时能连续跑几轮？失败与运动的哪个阶段相关？

**条件**：12 轴、30° 往返、单程 5 秒、100 Hz、连跑 5 / 10 / 20 轮。

**做法**：`bench_series.sh`，`SERIES` 分开命名便于事后归并。

**记录**：同 T3，另加每轮的跟随误差序列与运动阶段边界。

**看什么**：

- 失败落在"第几轮"的分布。若集中在第一轮或最后一轮，那是**条件性问题**（启动未稳 / 收尾动作），不是随机
- 失败时刻与运动相位的对应（加速段、匀速段、换向点）
- 同一根轴是否反复出问题
- **每根轴的跟随误差是否都在合理量级**。若某轴等于整条位移，那是"它一步没动"，而不是"它跟得不好"

**产出**：`T4_motion.md`：轮次分布、失败相位分布、逐轴跟随误差分布。

---

## T5 第一现场采集

**要回答**：异常发生的那一刻，各个量的先后顺序是什么。

**这不是一个独立任务**，它是 T3/T4 的采集方式：一旦检出异常，立即把异常前后各 200 拍的逐拍序列落盘。

**要看的先后关系**（G10）：

1. 同步裕量先变负，还是帧计数先变短？
2. 轴掉出 OP 之前，它的状态字有没有先变？
3. 主站侧先检出，还是驱动器侧先报？
4. 整帧未回与计数变短，谁先出现？

**产出**：附在每个异常的 `anomalies.tsv` 行里（`note` 列写时序结论）。

---

## T6 条件扫描

**要回答**：异常与哪个条件相关。**一次只动一个变量。**

### T6.1 重启间隔

0 / 5 / 20 / 60 秒，各 5 轮，其余条件固定。比较"失败轮次分布"。

### T6.2 轴数（降轴对照）

12 / 8 / 4 / 1。**只取这四个**，理由：

- 12 = 主对象
- 8 = 有一份现成部署档（`orangepi-bench-oct-30deg`），且是"第 8 台为 25:1"的混装点
- 4 = 中间规模
- 1 = 护栏最紧（2°）、换算单一，用来暴露多轴档放过的行为

**注意**：降轴要改接线。每次改线后必须重跑 T1。

### T6.3 观测开关

观测开 / 关各 5 轮。既是 G9，也是其它任务的对照。

### T6.4 单轴隔离

`ONLY_AXIS=N`，让 12 轴里只有一根动。用于判断"是这根轴自己的问题，还是多轴一起时的整体问题"。至少覆盖：全部一起动、只动最早出问题的那根、只动最后一根。

## T7 容错与恢复

**要回答**：坏了之后会怎样。

| 编号 | 条件 | 要回答 |
| --- | --- | --- |
| T7.1 | 运行中拔掉一处线缆 | 多久被检出；检出后主站做什么；其余轴如何 |
| T7.2 | 运行中让一根轴的驱动器掉电再上电 | 同上；恢复后该轴是否自动回来，还是需要重启会话 |
| T7.3 | 运行中强杀主站进程 | 驱动器进入什么状态；下次启动是否受影响 |
| T7.4 | 故障后不重启，继续发命令 | 命令被如何处置；有无部分生效 |
| T7.5 | 故障后按标准流程重启 | 能否回到与故障前等价的状态；等价性靠什么证明 |

**记录**：每个子任务都要留 `anomalies.tsv` 与逐拍序列。

**注意**：拔线与掉电是物理动作，需要事先约定由谁执行、在什么时刻执行，并把执行时刻记进 `condition.txt`。

## T8 长时行为

**要回答**：是否存在随时间劣化。

**条件**：12 轴、连续 1 小时以上（G8 的入门门槛由本文定在 1 小时，可调）。

**做法**：空转与运动各一次。每小时至少输出一次中间汇总（不必等结束）。

**看什么**：

- 帧计数异常、周期错失、同步裕量的**时间趋势**（不是极值，是趋势）
- 内存占用趋势
- 温度趋势（若可从驱动器读到）
- 前后半程的读数分布是否有差异

**产出**：`T8_longrun.md`：趋势图或分段统计。

---

## T9 读数自洽性

**要回答**：同一个事实，在不同字段里的说法是否一致（G11）。

**为什么单独列**：探查最终要靠读数下结论，读数之间不自洽时会导出错误结论，而这类问题不会自己暴露。

**做法**：对同一轮，交叉核对下列几组：

| 组 | 交叉核对 |
| --- | --- |
| 轴数与计数 | 期望计数与从站数的关系；`shutdown_in_op` 的分母与实际轴数 |
| 帧的两类异常 | 计数变短与整帧未回是否被分别计数；两者之和与总数是否自洽 |
| 停机状态 | 停机入口快照、停机后快照、报告里的终态三者是否一致 |
| 位置 | 命令下发的目标、驱动器回读的目标、实际位置三者的关系 |
| 同步 | 报告的相位/裕量与逐拍序列的一致性 |
| 运动完成标志 | 该标志与逐轴跟随误差是否说得通（例如"完成"但某轴误差等于整条位移） |

**产出**：`T9_consistency.md`：每组的核对结果，不一致的逐条列出。

---

## T10 观测自身影响

**要回答**：开着观测，是否改变了被测对象（G9）。

**做法**：观测开 / 关各 5 轮，同条件。比较异常率与首次异常时间。

**注意**：观测线程做 SDO 邮箱往返，而邮箱流量会占用总线的非周期带宽。这是真实影响，不是测量误差——要测的正是它有多大。

## T11 降轴对照的执行

T6.2 的具体执行方式，单列是为了强调它的代价：

# 6 从现象到问题

探查产出的是记录；**问题是从记录里判断出来的**。判断标准不是"低于某个值"，而是下列三条之一：

| 判据 | 含义 | 例子形态 |
| --- | --- | --- |
| P-1 没预料到 | 行为与设计意图不符，或与同条件下的其它轮次不符 | 同样的条件，一轮好一轮坏 |
| P-2 读数矛盾 | 同一事实在不同字段/不同来源说法不一致 | 报告说"在 OP"，快照说某轴不应答 |
| P-3 代价不可接受 | 行为本身可解释，但后果不能接受 | 一次异常导致其余全部轴停机 |

## 6.1 现象形态库

第 3.4 节的 `kind` 列从下列形态取，允许新增：

| 形态 | 可观测特征 |
| --- | --- |
| 计数变短 | 实得计数小于期望，且差值可被从站数解释 |
| 整帧未回 | 实得计数为 0 |
| 轴掉出 OP | 某轴 AL 状态为 20（SAFE-OP）或更早，带状态码 |
| 轴不应答 | 某轴 AL 状态读为 0（未应答） |
| 同步越限 | 同步裕量为负，或相位超出给定范围 |
| 周期错失 | 主站未能按周期发出 |
| 超预算 | 一周期内的工作超出预算 |
| 轴不执行 | 目标有效而该轴位置不动（跟随误差等于整条位移） |
| 启动失败 | 未进入运行态 |
| 停机异常 | 停机过程中出错，或停机后状态不符合预期 |
| 上报不自洽 | 同一事实在不同字段说法不同 |

## 6.2 结论的最低要求

每条结论必须能落到一句话：**"在 <条件> 下，观测到 <现象>，出现 <次数/位置>，<可复现/不可复现>。"**

达不到这一条的，写进 `notes.md` 的"没看懂的"一节，**不要写成结论**。

# 8 读数参考线（非判据）

下列数字只用于**从一堆轮次里挑出值得看的那几轮**，不产生结论，可随时按观察修订。

| 量 | 参考线 | 说明 |
| --- | --- | --- |
| 周期错失 | 0 | 主站吃满周期，值得单独看 |
| 超预算 | 0 | 同上 |
| 帧计数异常的**连续**数 | 短帧 5 / 整帧缺失 5 | **这是判定边界，不是参考线**。取自 `config/error_recovery_policies/<策略>.json` 的 `consecutive_error_threshold`；部署档用 `error_recovery_policy_id` 指定策略。两类各一套，并联 |
| 帧计数异常的**窗口**数 | 短帧 50 / 整帧缺失 50，窗口 60 秒 | 同上，是 `total_error_threshold`。**是滑动窗口不是整轮累计**——累计语义会让长跑必然自杀（配置里记着 2026-09-16 的现场） |
| 期望计数 | = 3 × 从站数 | 不是参考线而是恒等式；不成立说明装置构成变了 |
| 死轴 | 跟随误差 ≥ 该轴位移的 50% | 健康轴约 0.6–1.1°，死轴等于整条位移，中间空一个数量级 |
| 同步裕量 | > 0 ns | 负裕量意味着输出已迟到；注意开局收敛阶段本身会有负值，必须带交换号窗口看 |
| 连续迟到 | 5 次 | 驱动器自己的阈值是连续 6 次置 `0x001A` |
| 单次运行的时长 | ≥ 60 s | 短于此不足以让异常暴露 |
