# /verify — 本会话验证标准

调用时机：开始新的 P 项之前，或对上一会话的声称有疑问时。

## 核心规则

**任何声称必须在本会话窗口内有工具输出作为依据。**
上一会话的摘要、提交信息、注释里的描述，一律视为"待验证"，不是"已完成"。

具体类别：

| 声称类型 | 必须有的证据 |
|---|---|
| "编译通过" | 本会话 `cmake --build` 输出，无 error 行 |
| "字段 X 存在于类型 Y" | 本会话读过该头文件，且看见该字段 |
| "测试通过" | 本会话测试命令的输出，含 pass/fail 行 |
| "硬件行为 X 已验证" | 本会话在台架上运行的命令输出，或 run_report 内容 |
| "配置校验通过" | 本会话 `validate_runtime_config.py` 输出，退出码 0 |
| "代码逻辑正确" | 本会话读过相关文件，且能指出具体行号 |

## 开始新 P 项前的检查清单

1. 读 `docs/requirements/layering-plan.md`，找到目标 P 项的**完成判据**
2. 逐条列出判据，对每条确认：本会话能产生哪条证据？
3. 区分三类阻塞：
   - **离线可做**：纯代码修改、文档、配置 → 直接做
   - **需要编译**：在 Orange Pi 上 `cmake --build`，用 `python scripts/pi.py run` 执行
   - **需要台架运行**：驱动器上电，主站启动，观察实际行为

## P 项标记为完成的门槛

在 `layering-plan.md` 里把状态从空白改为 `**已完成**` 之前，必须满足：

- 完成判据里的每一条，在本会话内都有对应的工具输出证明
- 如果判据要求硬件验证，必须有 `scripts/pi.py run` 的实际输出，或 run_report 文件内容
- 如果判据要求"无编译错误"，必须有本会话的 `cmake --build` 输出

硬件无法获取时，可以标注 `**代码完成，待硬件验证**`，不能标 `**已完成**`。

## 对上一会话摘要的处理

摘要里出现的以下措辞，在本会话重新验证之前，一律降级处理：

- "编译干净" → "上一会话声称编译通过，本会话未验证"
- "已完成" → "上一会话标记完成，本会话未检查证据"
- "测试通过" → "上一会话声称通过，本会话未复现"

重新验证的方法：读相关文件 + 运行相关命令，拿到本会话的输出。
